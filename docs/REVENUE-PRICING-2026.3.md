# Revenue Pricing Contract 2026.3

## 목적

주거·상가·업무의 매각·임대 단가를 하나의 공통 숫자로 덮어쓰지 않고, 여섯 수익 풀마다 기준단가·보정·출처를 독립적으로 저장한다. 이 계약은 Stage 2 계획, Stage 3 정밀 계산, 민감도, 손익분기, Deal Rescue, 보고서와 검토 Snapshot이 같은 가격을 사용하게 한다.

계산 결과는 예비 타당성 값이다. `source-backed`는 연결한 원문의 형식과 메타데이터가 확인됐다는 뜻이며, 해당 비교사례의 적합성이나 감정평가 결론까지 보증하지 않는다.

## 버전

- 단가 Snapshot: `revenue-pricing-2026.3`
- 사용자 편집 계약: `revenue-pricing-input-2026.1`
- 수익 평가식: `revenue-valuation-2026.2`
- 면적 계약: `stage2-finance-area-2026.2`

`revenue-pricing-2026.2` 저장본은 읽을 때 2026.3으로 승격한다. 구형 통합 보정계수는 `use` 보정축으로 옮기고 최종 적용단가는 바꾸지 않는다.

## 여섯 가격 풀

| 수익 풀 | 기준단가 필드 | 단위 |
|---|---|---|
| 주거 매각 | `residentialSalePricePerSqM` | 원/㎡ |
| 상가 매각 | `retailSalePricePerSqM` | 원/㎡ |
| 업무 매각 | `officeSalePricePerSqM` | 원/㎡ |
| 주거 임대 | `residentialRentPerSqMMonth` | 원/㎡·월 |
| 상가 임대 | `retailRentPerSqMMonth` | 원/㎡·월 |
| 업무 임대 | `officeRentPerSqMMonth` | 원/㎡·월 |

구형 프로젝트의 `salePricePerSqM`과 `rentPerSqMMonth`는 같은 처분군의 초기 fallback으로만 쓴다. Stage 2 면적 계약이 있는 현재 프로젝트에서는 활성 수익 풀별 필드가 원문 근거 Gate의 필수 항목이며 공통 필드는 이를 대신하지 않는다.

## 단가 계산

각 풀은 보정 전 기준단가와 다섯 보정축을 보존한다.

```text
통합 보정계수 = 용도 × 입지 × 층 × 면적 × 신축 보정
최종 적용단가 = 보정 전 기준단가 × 통합 보정계수
```

각 보정축은 다음 값을 가진다.

- `factor`: 0 초과 10 이하의 배수
- `status`: `not-applied`, `internal-assumption`, `user-input`, `source-backed`
- `sourceName`, 선택적 `sourceRef`, `asOf`, `note`

`source-backed` 보정은 문서 참조와 유효한 기준일이 모두 있어야 한다. 다섯 축 중 하나가 누락되거나, 축의 곱과 통합 보정계수 또는 최종 적용단가가 맞지 않으면 계산을 중단한다.

현재 상가 임대의 초기값은 공통 임대 기준단가에 `use = 1.20` 내부 가정을 적용한다. 이는 시장 확정값이 아니며 상가 임대사례로 교체하거나 보정해야 한다. 다른 풀에는 이 프리미엄을 자동 적용하지 않는다.

## 가격 출처 상태

| 상태 | 의미 |
|---|---|
| `internal-assumption` | 내부 초기값 또는 분석용 비례 조정 |
| `user-input` | 사용자가 직접 입력했으나 원문이 연결되지 않음 |
| `source-backed` | 허용된 원문 종류, 문서 참조, 기준일과 검증자가 확인됨 |

원문 근거 가격이 있으면 그 기준단가가 사용자 기준단가 초안보다 우선한다. Stage 3의 기준단가 입력은 잠기며, 원문 근거 패널에서 값을 수정하거나 근거를 제거해야 한다. 보정축은 기준단가 출처와 별도로 편집할 수 있다.

## 단계 전환

1. Stage 2가 실제 층별 프로그램에서 여섯 수익 면적을 만든다.
2. Stage 2가 독립 가격 Snapshot으로 풀별 매출, 잠재 임대료, 유효총수입, 운영비, NOI와 가치를 잠근다.
3. Stage 3는 Scenario 가격이 있으면 이를, 없으면 Stage 2 잠금 가격을 사용한다. 구형 시나리오만 공통 가정에서 가격을 생성한다.
4. Stage 3에서 가격이나 보정을 바꾸면 Stage 2 잠금값과 현재값을 풀별로 `review` 대사한다.
5. 저장한 Stage 3 Scenario에는 현재 가격 Snapshot이 포함되고, 단가 변경은 검토 Snapshot SHA-256을 바꾼다.

## 민감도와 역산

민감도, 손익분기, 생존선과 Deal Rescue는 선택한 처분군의 활성 풀 최종단가를 면적으로 가중한 값을 축으로 사용한다. 목표 단가가 바뀌면 풀 사이의 상대 가격과 각 보정계수는 유지한 채 해당 처분군의 기준단가를 같은 비율로 조정한다.

매각과 임대가 함께 있는 혼합안은 기존 비교 계약과 같이 매각 단가를 1차 수익 민감도 축으로 사용한다. 임대 단가, 공실률과 Cap rate는 독립 입력 및 별도 하방 검토 대상이다.

## Workspace와 보고서

- 계획안별 기준단가·보정 초안은 `ProjectWorkspace` 불변 revision에 저장한다.
- 다른 프로젝트의 초안, 존재하지 않는 금융 시나리오, 유한하지 않은 기준단가, 범위 밖 보정계수는 Workspace 저장을 거부한다.
- Plan Studio는 기준단가, 활성 보정, 최종 적용단가와 출처 상태를 표시한다.
- Stage 3는 활성 풀만 편집하며 원문 근거 단가는 직접 덮어쓰지 않는다.
- 보고서는 보정 전 기준단가, 보정축, Stage 2 잠금값, Stage 3 현재값과 출처를 나란히 표시한다.

## 회귀 기준

- 여섯 풀을 서로 다른 단가로 평가해 각 매출·가치가 독립적으로 계산된다.
- 다섯 보정축의 곱과 최종단가 불일치를 탐지한다.
- 2026.2 통합 보정을 승격해도 최종단가가 변하지 않는다.
- 한 풀의 사용자 초안이 다른 풀 단가를 바꾸지 않는다.
- 공통 가격 원문은 fallback이 되고 개별 풀 원문이 우선한다.
- 원문 Gate는 실제 면적이 있는 활성 풀만 요구한다.
- 가격 Snapshot이 있는 시나리오의 민감도·손익분기·Deal Stress·Deal Rescue가 동결되지 않는다.
- 가격 초안은 Workspace capture/apply에서 다른 프로젝트 상태를 지우지 않는다.
- 독립 풀 단가가 바뀌면 Stage 3 저장본과 검토 Snapshot Key가 바뀐다.

## 미확정 경계

- 비교사례 자동 선별과 위치·층·면적·신축 보정계수 산출 모델은 아직 감정평가 검증을 거치지 않았다.
- 현재 보정축은 사용자가 근거와 함께 입력하는 계약이며 자동 시장 추정치로 표시하지 않는다.
- 임대료 원문, 운영예산, Cap rate와 안정화 계수는 서로 다른 근거가 필요하다.
- 실제 투자·대출·보험 판단 전 감정평가사, 중개사, 금융기관과 해당 전문가의 검토가 필요하다.
